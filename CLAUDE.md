# Systema Naturae

Interactive taxonomy portal. Each family lives in its own directory under `taxonomy/`; the portal aggregates them at build time.

> Navigation architecture documented in [`docs/navigation.md`](docs/navigation.md).

> **⚠️ Six kingdoms, one system.** `portal/data/kingdom-config.json` declares
> `animalia`, `plantae`, `fungi`, `chromista`, `protozoa` and `archaea`. They are
> peers: each has its own taxonomy input, its own colour registry and its own
> output directory, and all are built the same way by the same code. The
> restructure that used to be planned here is done — every family now lives at
> `taxonomy/<kingdom>/<phylum>/<class>/<order>/<family>/`, and there are no
> family directories at the repo root.
>
> The live/deployed portal is still **animalia only**; the other five are built
> on demand (`npm run build:plantae` and siblings). Their inputs are separate
> files — do not graft plant nodes into `taxonomy.json` or vice versa.

## Commands

```bash
cd portal && npm run dev          # rebuild the tree, start dev server
cd portal && npm run build        # rebuild the tree, production build
cd portal && npm run build:plantae   # build one non-animal kingdom (SN_KINGDOM=plantae)
cd portal && npm run build:fungi     # …and fungi, chromista, protozoa, archaea
cd portal && npm run build:all    # build every kingdom in kingdom-config.json, then vite build
cd portal && npm run typecheck    # TypeScript check
cd portal && sh scripts/buildData.sh   # rebuild animalia only (fast verify; auto-detects bun vs tsx)
cd portal && SN_KINGDOM=plantae sh scripts/buildData.sh  # rebuild plantae only
cd portal && npm run build:unified     # opt in to writing the monolithic tree
```

`SN_KINGDOM` selects the kingdom (default `animalia`); everything else comes
from `kingdom-config.json`. The npm `build:`/`dev:` scripts and
`buildAllKingdoms.sh` all pass `NODE_OPTIONS=--max-old-space-size=8192`, which
large kingdoms need to avoid OOM.

By default the build writes the **skeleton, the per-order files and the
manifest** — the artifacts the app actually reads. The monolithic
`unified-taxonomy.json` is **opt-in** (`SN_BUILD_UNIFIED=1`), because it is a
hundreds-of-MB file that only the build tooling consumes, and one changed
family forces a full re-serialisation of it. See
[`docs/build-structure.md`](docs/build-structure.md).

Kingdoms are declared in `portal/data/kingdom-config.json` (input file, output suffix,
color registry per kingdom). `buildData.ts` selects the kingdom via `SN_KINGDOM`
(default `animalia`) and reads the rest from that config. The npm `build:`/`dev:`
scripts and `buildAllKingdoms.sh` all pass `NODE_OPTIONS=--max-old-space-size=8192`,
which large kingdoms need to avoid OOM.

## Graph UI features

The Coverage modal (ⓘ button) shows per-class statistics with sort/filter controls. Rank counts (Phylum, Class, Order, etc.) are stamped on the root node at build time and displayed live in the top header bar.

### Node sizing
`nodeR()` in `FamilyTree.tsx` uses widened radii: family (12), subfamily (9), genus (6.5), species (2.5). Provides clearer hierarchy distinction.

### Family focus pruning
When a family is focused in the tree, all non-focused families' children are pruned to single dots. The focused family gets the full circle naturally without arc remapping.

### Genus rank badge
`UnifiedInfoPanel.tsx` shows a `GENUS` rank badge with accent colour in `GenusPanel`.

### Coverage modal
The ⓘ Coverage button opens a modal with sort/filter controls (Gaps first / A–Z; All / Complete / Partial / Gaps), per-class mini progress bars, and family status tags.

### Wheel of Nature, Statistics Header, Book View, Species of the Day
All shipped — see `portal/src/components/`. Open items live in the root
`BACKLOG.md`, under *Folded in from `docs/backlog.md`*.

## Adding a new family — checklist

1. **`taxonomy/<kingdom>/<phylum>/<class>/<order>/<family>/src/data/<family>.json`** — species data.  
   Root: `{ id, name, rank: "FAMILY", commonName, children: [...] }`  
   Node fields: `lineage`, `continents[]`, `subspeciesCount`, `description`, `namedAfter`, `sourcedFrom`

2. **`portal/data/taxonomy.json`** — add a FAMILY node with `appSlug` and `speciesCount` (real-world total, used by Coverage modal) inside the correct ORDER/CLASS.

3. **`portal/src/colorRegistry.ts`** — add a `ColorTheme` constant and register it in `COLOR_REGISTRY` under the `appSlug` key.

4. Run `cd portal && sh scripts/buildData.sh` to verify — warns on missing data files, prints total node count.

5. **Check `shared/data/pending-eponyms.json`** — if the new family's `familySlug` appears there, add those species with their `namedAfter` field and remove the entry.

6. **Regenerate gap reports** so the new family appears in tracking:
   ```bash
   cd portal
   npx tsx scripts/findGaps.ts
   npx tsx scripts/reportPhyla.ts
   npx tsx scripts/generateGapTasks.ts
   ```

## How the graft works

`buildData.ts` walks `taxonomy.json`, tracking the current KINGDOM, PHYLUM, CLASS and ORDER as it descends. When it hits a FAMILY node with `appSlug`, it resolves the file through `portal/scripts/lib/familyPath.ts` — the single authority for family→path, which walks the KINGDOM and PHYLUM levels too and handles a phylum with no CLASS (Tardigrada resolves under `taxonomy/animalia/tardigrada/`) — then stamps every descendant node with `familySlug`, `className`, `orderName`, and `extinct` (detected from `†` prefix or "extinct"/"fossil" in description), and splices the children in.

After grafting, a **compression pass** walks every GENUS: minimal SPECIES children (no real description, no children of their own) move into a flat `speciesList[]` on the genus, dropping their tree weight. `colorRegistry.ts` uses `familySlug` to look up the `ColorTheme` for rendering.

## Key TaxonNode fields

| Field | Where set | Purpose |
|---|---|---|
| `namedAfter` | family JSON | Person species is named after; shown in tree tooltip and Eponyms modal |
| `familySlug` | buildData.ts | Stamped at build time; used for color lookup and navigation |
| `className`, `orderName` | buildData.ts | Stamped at build time; used by Coverage modal and panels |
| `extinct` | buildData.ts | Auto-detected from `†` prefix or "extinct"/"fossil" in description |
| `sourcedFrom` | importer | `"wikipedia"`, `"gbif"`, `"ollama"`, etc. Used by OptionsPanel highlight toggle |
| `iucnStatus` | wiki-images.json merge | IUCN red-list status code (e.g. `LC`, `EN`, `CR`) |
| `speciesCount` | taxonomy.json | Real-world species total for the family (not portal node count) |
| `continents[]` | family JSON | Either continent codes (`"NA"`, `"EU"`) or full names — both accepted |

## Sidecar data: `shared/data/wiki-images.json`

Keyed by scientific name. ~148k entries; ~34k carry an `image` URL, ~33k a `commonsCat`, ~31k an `iucnStatus`, ~10k `rangeMaps`. Populated by `scripts/fetchWikidataImages.ts` from Wikidata SPARQL. Consumed at runtime by `UnifiedInfoPanel` and `ImageTabs`. Kept out of the tree entirely, so neither the skeleton nor the per-order files grow.

## Offline Wikipedia pipeline (Macie only)

A 2026-06-01 enwiki dump lives on external volumes — see global `~/.config/opencode/AGENTS.md` for paths. The pipeline:

1. **`scripts/buildWikipediaDb.py`** parses the raw multistream dump into `/Volumes/WikiDump/wiki-pages.sqlite` (title → wikitext). Use `tailWikiDbProgress.py` to watch progress; `watchWikipediaDump.sh` waits for the volume.
2. **`scripts/mergeWikiInfoboxes.ts`** parses infoboxes out of the SQLite DB and merges descriptions/continents/IUCN into family JSONs.
3. **`scripts/enrichFromWikipedia.ts`** (root) uses the SQLite DB when mounted, falling back to the Wikipedia REST API otherwise. `portal/scripts/enrichFromWikipedia.ts` is the REST-API-only sibling.

Toggle the "Highlight Wikipedia species" checkbox in the ⚙ OptionsPanel to see which species carry `sourcedFrom: "wikipedia"`.

## Family patterns

- **Full sub-app** (`taxonomy/animalia/chordata/mammalia/carnivora/felidae/`, `…/canidae/`) — has `App.tsx`, `colors.ts`, `vite.config.ts`; runs standalone and in the portal. These two are the only ones today.
- **Data-only** (e.g. `taxonomy/animalia/chordata/aves/passeriformes/corvidae/`) — only `src/data/<family>.json`; portal-only until a full app is built.

The Growth tab in the Coverage modal shows the import timeline with cumulative species/node growth, togglable series (cumulative species, per-batch bars, total nodes), and tooltips with batch details.

## Gap tracking

- `portal/scripts/findGaps.ts` → `portal/data/gap-report.json` (per-family `have` / `speciesCount` / `gap`). Kingdom-aware: `SN_KINGDOM=plantae` reads `taxonomy-plantae-snippet.json` and writes `gap-report-plantae.json` (input/output resolved via `kingdom-config.json`).
- `portal/scripts/reportPhyla.ts` → `docs/gap-tasks-phyla.md` (phylum/class roll-up). Also POSTs to `localhost:9876` if `phylumProgressd.ts` is running.
- `portal/scripts/generateGapTasks.ts` → `docs/gap-tasks.md` (per-family TODO list).
- `portal/scripts/phylumProgressd.ts` — long-running daemon that records each POST so progress is graphable over time.

Always run these three after a significant import.

## Fixing sanity issues

`portal/data/sanity-queue.json` is currently `[]` — all 4057 historical issues across 66 families have been resolved (full report in `sanity-issues.json`). Fix scripts live in `scripts/`:

| Script | Fixes |
|---|---|
| `fix_continents.py` | Replaces abbreviated continent codes (`"EU"` → `"Europe"`) with full names |
| `fix_duplicates.py` | Removes duplicate species entries |
| `fix_empty_genera.py` | Removes genus nodes with no children |
| `fix_lineage.py` | Infers missing `lineage` field from parent genus |
| `fix_subspecies.py` | Adds `subspeciesCount: 0` to species nodes missing it |
| `fix_all_descriptions.py` | Generates descriptions for all species based on lineage/genus |
| `fix_redirect_descriptions.py` | Clears genus-article text off species nodes (the Wikipedia redirect bug) |

**Workflow for a new sanity scan:**
1. Run each fix script from repo root
2. Rebuild and verify: `cd portal && sh scripts/buildData.sh`
3. Update `sanity-queue.json` to reflect remaining issues

## Playwright tests

Tests live in `portal/tests/`. Always use an isolated browser context when running Playwright — the default `test` fixture already provides one, but when launching directly via `browser.newContext()` pass `{ storageState: undefined }` to avoid leaking Google/other credentials. Run with:

```bash
cd portal && npx playwright test              # headless
cd portal && npx playwright test --headed     # visible browser
```

# Graph vs Book — parity audit

*Audit date:* 2026-09-26 · *Surfaces:* portal `Graph` and `Book` viewModes

## How the two surfaces get their data

Not a fair fight, which explains most of the differences below:

| | Graph | Book |
|---|---|---|
| Tree | `unified-taxonomy.json` — **compressed**: well-described species become nodes, the rest flatten into genus-level `speciesList[]` | the *uncompressed* per-order files, deliberately (see `useBookChapters.ts` header) |
| Materialised species | 64,695 described | ~1.2M entries |
| Images / IUCN | `shared/data/wiki-images.json` + live REST lookup | generated sidecar `portal/public/data/book/extensions*/` |
| Family prose | the family JSON's own `description` | `familyIntros.ts` **overrides** it |
| Coverage stats | Coverage modal | `chapterStats` inline per family |

The sidecars are generated by `portal/scripts/ensureBookData.sh` and are
**gitignored** (`portal/public/data/book/`), so a stale sidecar only ever
affects a local checkout, never a shipped build. They were 11 days stale at
audit time; rebuilt.

## Graph → Book (graph has it, book does not)

### 1. The whole PHYLUM rank — the only real structural gap

32 animalia phyla, all 32 carrying a description, and the book has no phylum
level anywhere: it goes kingdom-selector → Part (CLASS) → Chapter (ORDER) →
Family → Genus → Species. PHYLUM and KINGDOM are absent from the per-order
files entirely (those files are rooted at ORDER), so this is structural, not a
slicing bug. Filed as a backlog item rather than fixed here.

### 2. Subspecies

851 subspecies nodes. The graph lists them per species and splits them into
accepted (845) and "Historical / not COL-accepted" (6). The book shows only a
count via `subspeciesCount`.

Mitigated: just 2 of 851 subspecies carry a description, so the loss is names
and the accepted/historical distinction, not prose. Deliberate, documented in
`shared/src/book/components/SpeciesEntry.tsx:154`.

### 3. Breed portraits — 89 breeds had a photo in the graph and none in the book

The graph's `BreedPanel` fetches a portrait live from the REST API by
`wikipediaTitle`. The book can only use `shared/data/breed-images.json`, which
covered **232 of 321** breeds; the 89 without were exactly the ones folded in
out of the retired `breeds.ts`. **Fixed** — see "Remediation" below.

### 4. `taxonomicNote`

3 families, graph only (`UnifiedInfoPanel.tsx:306`). Negligible.

### 5. Graph-only chrome

Search, Coverage modal, Eponyms modal, Wheel of Nature, Species of the Day,
International Days, HabitatMap, family focus/pruning, wild-parent navigation.
App features rather than data.

## Book → Graph (book has it, graph does not)

### 1. Curated family intros — **clashed, fixed**

`experiments/book-view/src/familyIntros.ts` holds 29 hand-written family
intros, and `decorateChapter.ts:35` **overwrites** the family description with
them. 19 of those families also had their own Wikipedia-derived description in
the family JSON, so the same family showed two different texts depending on
which surface you were on. Leporidae:

- graph — *"Leporidae is the family of rabbits and hares (Lepus), containing
  over 70 species of extant mammals in all…"*
- book — *"Rabbits and hares — fast-breeding, long-eared lagomorphs found on
  every continent but Antarctica, distinguished from rodents by a second,
  smaller pair of upper incisors."*

**Fixed** by promoting the curated prose into the family JSON so both surfaces
read one source.

### 2. Synonym tagging

`shared/src/book/lib/synonyms.ts` marks a species whose description came from a
synonym ("syn. of *Felis catus*") and links the accepted name. Imported only by
the book; the graph has no synonym layer at all. Its three `synonym` matches in
`UnifiedInfoPanel.tsx` are the unrelated subspecies `accepted` flag.

### 3. `chapterStats` prose

"N of M entries fully described so far" per family. The graph conveys coverage
only through the Coverage modal, in a different form.

### 4. "Also in this genus: …"

The book rolls the compressed `speciesList[]` species up into a name list. The
graph shows them as pruned dots instead.

### 5. Part framing and toggles

Part/Chapter numbering, the per-Part 7×7 collage, the Part intro (from the CLASS
description), and the three persisted toggles `showExtinct`, `showStubs`,
`showEmptyFamilies`.

## Clashes — same data, two treatments

### 1. Contradictory family prose — **fixed**

See Book → Graph #1 above. The only genuine contradiction found.

### 2. Default scope differs by 67%

The book hides families whose `enrichedCount === 0`: **5,384 of 8,043**. The
graph shows all 8,043. Toggleable via `showEmptyFamilies` and deliberate — the
comment in `FamilySection.tsx:76` says it stops the book filling with bare
headers — but the default reading experience covers a third of the tree.

### 3. `family.distribution` is rendered but never populated

`FamilySection.tsx:133` prints it, but it is 0/5,070 families in animalia *and*
0/1,259 in plantae. `distribution` is a **species**-level field (5,122 species
carry it). The family-level render is dead code.

### 4. `notableMembers` — mostly parity

376 families carry it. The graph always shows it; the book shows it only when
the family has no description. Acceptable.

## Checked and found fine

- `notableMembers` and `speciesCount` are populated on all 8,043 families and
  rendered on both surfaces.
- PHYLUM/KINGDOM being absent from the order files is by design.
- Compressed vs uncompressed species granularity is the documented reason the
  book does not read `unified-taxonomy.json`.
- The stale sidecar, while real, never ships — they are gitignored.

## Remediation applied

### 1. Family intros — 19 contradictions resolved

This took **two** fixes, and the first alone was not enough.

The 19 curated intros that contradicted a family description were promoted onto
the FAMILY node in `portal/data/taxonomy.json` (where family prose actually
lives — the per-family data JSONs carry no family-level `description`, so
patching those is a silent no-op).
`familyIntros.ts` keeps the 10 that fill genuine gaps, restoring the contract
its own header states: a family the portal has enriched must not be listed
there. Done by `scripts/reconcileFamilyIntros.py`.

But the graph still disagreed, because `FamilyPanel` never read
`node.description` at all — it rendered a **live** Wikipedia REST summary and
ignored the stored prose entirely. So the clash was never "JSON vs curated
intro", it was "live extract vs curated intro", and promoting the intro changed
nothing on the graph side until `FamilyPanel` was changed to prefer
`node.description` and fall back to the live extract, exactly as `BreedPanel`
now does. Verified in-browser on 4 of the 19.

### 2. Breed portraits — 232 → 306 of 315 breeds

New `scripts/enrichBreedsFromWikipedia.py --portraits`, which fetches each
breed's portrait from the article title the validated resolution already
produced, rather than from a name search. It:

- filled the 89 breeds that had no portrait at all;
- corrected all 7 demonstrably wrong portraits (`Alpine` → *Troupeau chèvres
  alpines*, `Chinese` → a domestic goose, `Duroc` → a pig, `African` → an
  African goose, `Yorkshire` → a Large White pig, `Californian` → a Californian
  rabbit, `Embden` → a domestic goose);
- fell back to the Wikidata item's P18 when an article has no lead image, taking
  the QID from the mirror rather than the REST summary — the summary answers
  `Q141438738` for *Alpine goat*, which has no picture, where the mirror's
  `Q2840092` is the goat breed and has one;
- **declined** to attach a portrait for the 6 breeds that exist only as a
  section of a "List of … breeds" article, because that page's lead image
  belongs to a different breed on the list. Four cavies were previously showing
  a Peruvian cavy and one a Spanish coat of arms; they now show no picture
  rather than a wrong one;
- normalised every stored value to a bare Commons filename, dropping the
  `?utm_source=…` tracking query the REST API appends. Absolute URLs bypass
  `Special:FilePath?width=N`, so the book's hover preview and lightbox could not
  resize them.

**The name collisions are now fixed too.** `breed-images.json` and the book's
per-chapter `images` map are keyed by host species as well as breed name
(`cat-Abyssinian`, `cavy-Abyssinian`, `cattle-Hereford`, `pig-Hereford`,
`rabbit-Rex`, `chicken-Silkie`, …), so all 6 pairs are distinct and each holds
its own animal — `cattle-Hereford` gets the cow that `pig-Hereford` never
showed. The key is derived in one place, `shared/src/book/lib/breedKey.ts`, and
mirrored in `scripts/enrichBreedsFromWikipedia.py`; the generator
(`extractSlice.ts`) and the runtime reader (`decorateChapter.ts`) both go
through it, and `fetchBreedImages.mjs` — the name-search tool that caused the
wrong portraits in the first place — now refuses to run.

The host *species* is the discriminator rather than the family, because caprinae
holds both sheep and goats and anatidae both ducks and geese, so no per-family
animal word can be correct.

Also fixed along the way: the resolution table had `pig Hampshire` pinned to
`Hampshire Down`, the *sheep's* article, so the pig breed was taking the
sheep's prose and portrait. It is now `Hampshire pig`.

### 3. Backlog

The phylum level is filed in `BACKLOG.md` rather than fixed — it is a design
call about the book's structure, not a defect.
